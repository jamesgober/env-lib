# v1.0.0 — Stable API

`env-lib` is released directly as 1.0. This is its first release. The public API, the `.env` file format, and the save guarantees are frozen for the 1.x line under [`STABILITY-1.0.md`](../STABILITY-1.0.md). Every later 1.x release is backwards compatible with this one.

## What `env-lib` Is

Application environment variables for Rust. An `Env` holds the variables that belong to one application: set, read, and remove them in code, save them to a `.env` file, and load that file the next time the program starts. The file can be edited by hand between runs or while the program runs; a save keeps those edits exactly as written. The variables can be exported under a namespace prefix to a child process or to the current process. The system environment is read as a fallback but never copied into an `Env` or saved. The only dependency is `path-lib`, a first-party crate with no dependencies of its own.

```rust
use env_lib::Env;

let app = path_lib::App::new("HiveDB")?;
let mut env = Env::for_app(&app)?;

env.set("PORT", "7000")?;
env.remove("LEGACY_MODE");
env.save()?;

let port: u16 = env.parse("PORT")?.unwrap_or(8080);
# Ok::<(), env_lib::Error>(())
```

```toml
[dependencies]
env-lib = "1.0"
```

## Features

### Variables in code

- **`set`, `remove`, `clear`** change the variables in memory. Names are checked when set: ASCII letters, digits, and `_`, not starting with a digit, at most 255 bytes. Values may hold anything but NUL, up to 32,767 bytes, which is the Windows per-variable limit, so every accepted value can be exported on every platform.
- **`get`** returns the `Env`'s own value, or `<prefix><key>` from the process environment when the `Env` does not have it. **`get_or`** adds a default, **`parse::<T>`** parses into any `FromStr` type, and **`flag`** reads `true`/`1`/`yes`/`on` and `false`/`0`/`no`/`off` in any case.
- **`system(name)`** reads a system variable such as `PATH` exactly as named.

### The `.env` file

- **`Env::open(path)`** loads a file, or starts empty when it does not exist yet, and ties the `Env` to that path. **`Env::for_app(&app)`** uses `.env` in the application's config directory as resolved by `path-lib`.
- **`save`** re-reads the file and applies this session's changes to it, **`save_to(path)`** merges every variable into another file and ties the `Env` to it, and **`reload`** discards unsaved changes and picks up edits made outside the program.
- **Hand edits survive a save.** Because a save applies only the variables set or removed in this session to the file as it is on disk, edits made by hand while the program runs are kept, and the `Env` holds them after the save. When both changed the same variable, the program's value wins.
- **Lossless saves.** Comments, blank lines, ordering, CRLF line endings, and the exact text of every untouched entry are written back unchanged. Changed values are updated in place and keep their inline comments, removed variables are dropped, duplicates collapse to the last occurrence, and new variables are appended.
- **Atomic and private.** Saves go through `path_lib::write_atomic`, so readers see the old file or the complete new one. Missing directories are created. A new file is `0600` on Unix; an existing file keeps its permissions.
- **Familiar syntax.** `#` comments, `export NAME=value`, single quotes for literal text, double quotes with `\n`, `\r`, `\t`, `\"`, `\\`, and `\$` escapes, and quoted values spanning lines.
- **Strict parsing.** A malformed line fails the load with `Error::Syntax` and its 1-based line number; nothing is skipped. `${VAR}` interpolation is not performed, so a value is exactly what the file says.

### The namespace prefix

Names are plain in code and in the file (`PORT`). Only the copies placed in a process environment carry the prefix (`JG_PORT` by default), so application variables do not collide with system ones. `with_prefix("HIVE_")` changes it; an empty prefix falls back to `JG_`, and a prefix that is not a valid shell name, such as `JG.`, is rejected. A name passed with the prefix addresses the same variable as the plain name.

### Handing variables to other code

- **`apply_to(&mut Command)`** sets the prefixed variables on a child process and removes ones deleted since the last export. The parent's environment is untouched, so it is safe.
- **`export()`** writes the prefixed variables into the current process environment, for third-party code that reads `std::env` directly. It is an `unsafe fn` with the same contract as `std::env::set_var` in edition 2024: call it at startup, before any other thread exists.

### Secrets

Values never appear in `Debug` output or in errors, which tend to end up in logs. Errors name the variable, the file, and the line instead. On Unix, a file created by a save is readable only by its owner.

## The Stable Surface

Every item re-exported from the crate root is part of the 1.x contract.

- **`Env`:** constructors `new`, `open`, `for_app`, `from_text`; `with_prefix`, `prefix`, `file`; reads `get`, `get_or`, `parse`, `flag`, `contains`, `len`, `is_empty`, `iter`, `is_dirty`; writes `set`, `remove`, `clear`; persistence `save`, `save_to`, `reload`; hand-off `apply_to`, `export`.
- **Free function:** `system`.
- **Constants:** `DEFAULT_PREFIX`, `FILE_NAME`, `MAX_KEY_BYTES`, `MAX_VALUE_BYTES`, `MAX_FILE_BYTES`.
- **Errors:** `Error`, `Result`.

The accepted file syntax, the save guarantees, the naming rules, the default prefix, and the guarantee that values never appear in errors or `Debug` output are part of the contract as well. The full list, and what may still change in minor releases, is in [`STABILITY-1.0.md`](../STABILITY-1.0.md).

## Verification

- **Tests.** 69 tests on Windows: 35 unit tests, 20 file workflow tests, 1 export test, 3 property tests, and 10 documentation examples. Linux adds a Unix-only test that checks the `0600` mode of new files and that an existing file keeps its permissions. All pass on stable and on MSRV 1.85.
- **Property tests.** 1024 cases each: any set of variables, with names and values including quotes, backslashes, `$`, `#`, newlines, carriage returns, tabs, and arbitrary Unicode, survives a save and a load unchanged; the parser never panics on arbitrary text; and opening and saving a file without changes is byte-identical.
- **End-to-end sessions.** Integration tests create, edit, delete, and reload variables across separate `Env`s as separate runs would. They check that hand edits are kept verbatim, including edits made while the program runs; that a removal in code wins over a concurrent hand edit; that a changed value keeps its inline comment; that `save_to` merges into an existing file; and that CRLF files stay CRLF. They also cover missing directories, malformed, oversized, and non-UTF-8 files, and `~` expansion. The `export` test runs in its own test binary, so no other test touches the process environment at the same time.
- **Coverage.** Line coverage measured with `cargo-llvm-cov` is about 98% on Windows and Linux. The unexecuted lines are I/O failure branches that cannot be forced safely, such as a read failing after the file has been opened.
- **Lints.** `clippy::pedantic` is clean for `x86_64-pc-windows-msvc`, `x86_64-unknown-linux-gnu`, `aarch64-apple-darwin`, and `x86_64-unknown-freebsd`.

## Performance

| Operation | Median |
|---|---|
| Parse 10 entries | 3.95 µs |
| Parse 1000 entries | 450 µs |
| `get`, held by the `Env` | 15.0 ns |
| `get`, prefixed name | 15.9 ns |
| `get`, falling back to the process environment | 156 ns |
| `parse::<u32>` | 73 ns |
| `set`, updating an existing value | 87 ns |

Measured on Windows 11, x86_64, with criterion 0.5. A lookup the `Env` can answer costs one hash lookup and no allocation; a miss is dominated by the operating system call that reads the process environment. `save` is not benchmarked: its cost is the flush to disk in the atomic write, which depends on the storage device rather than the crate. Full methodology and results are in [`docs/PERFORMANCE.md`](../PERFORMANCE.md).

## Compatibility

- **MSRV:** Rust 1.85, frozen for 1.x
- **Edition:** 2024
- **Platforms:** Linux, macOS, Windows (FreeBSD and other Unix systems follow the Linux behaviour)
- **Dependencies:** `path-lib` 1.0
- **Thread safety:** `Env` is `Send + Sync`. Reads through `&Env` are safe from many threads; changes need `&mut Env`, so wrap a shared, changing `Env` in a `RwLock`.
- **Concurrent processes:** each save applies only that process's own changes to the latest file, so two processes changing different variables both keep their changes; for the same variable, the last save wins. Each save is atomic, but the read at its start and the final rename are not locked, so a write by another process in between is overwritten.

## Out of Scope

These were considered for 1.0 and left out on purpose:

- **Layered files** such as `.env` plus `.env.local`. Open two `Env`s and read from the more specific one first.
- **File watching and automatic reload.** It needs OS notification APIs and, in practice, a dependency. Call `reload` when the file may have changed.
- **Encrypted values.** Key management belongs in a secrets manager, not in a `.env` file.
- **`${VAR}` interpolation.** A file could then pull arbitrary environment state, including secrets, into a value. It is not supported, by design.
- **Per-variable prefixes.** One namespace prefix applies to every variable of an `Env`. Use separate `Env`s for separate namespaces.
